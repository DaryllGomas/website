01The problem

Remote support usually means trusting someone else's master key.

Small clients need help on their own computers. The usual options are per-device fees for a commercial remote-management tool, or a vendor whose one server can command every PC it manages. If that server is breached, every client is exposed.

The free open-source route has its own catch: a self-hosted RustDesk server normally needs ports forwarded through the router, any computer can register with it, and the one key that guards connections is handed to every client.

Heimdall, the Norse guardian of the rainbow bridge, opens the bridge only for those allowed.

02What I built

A locked-down service around open-source RustDesk.

  • A hardened RustDesk server. I patched the open-source server so devices check in over one encrypted web connection, and only if I approved them.
  • The Heimdall console. My own service for setup links, approvals, removal, session alerts and a 12-month connection log, behind passkey sign-in.
  • Setup with no scripts. The client opens a link, installs the official signed RustDesk app and reads me a code. Nothing to type in a terminal.
  • Its own walled-off server. A small virtual machine on its own network segment, sharing nothing with my own systems.
  • Wired into my invoicing app. A client's card has Add a PC and Connect buttons.

Built on the open-source project's newest hardened code, not its older release. The RustDesk app on the client's PC is the official, signed app, unchanged.

03How it works

One door in. Nothing reaches back.

1 · Client PC

  • Official, signed RustDesk app
  • Connects outward only, over an encrypted WebSocket
  • No port forwarding needed on the client's router

2 · One door

  • A Cloudflare Tunnel, started from inside
  • Exposes a short list of paths; everything else is refused
  • No ports opened on the home router

3 · Server

  • Hardened RustDesk server: allowlist, pinning, limits
  • Heimdall console: invites, approvals, removal
  • Its own firewall blocks everything else, in and out

4 · My side

  • Console behind a passkey
  • Invoicing app: Add a PC, Connect
  • An alert on every session request, and a 12-month connection log

How access is locked down

Lock 1 · adding a PC

A code only the client sees

No PC joins until the client reads me the 7-digit code from their own screen. A stranger's machine doesn't get that approval.

Lock 2 · the console

A passkey, not a password

Approving and removing PCs sit behind my passkey. The console has no password to phish, guess or reuse.

Lock 3 · every session

The client says yes

Every session needs the client to click Accept on their own screen, unless they chose to set up unattended access with a password. Either way, an alert fires and the connection is logged.

Walls inside walls

The internet
One tunnel
Own segment
Approved PCs
  • A short list of paths through the tunnel. Everything else gets a "not found". No port forwarding is needed, on my router or a client's.
  • A segment that can't reach home. My desk can reach the server; the server is blocked from reaching back into my network.
  • Only approved, pinned PCs. The device list is checked before anything else happens, then again inside the sign-in.
  • Every session announced. An alert on every session request, and a connection log kept for 12 months.

06How it's tested and run

Reviewed first, then tested over a real connection.

  1. Rules firstI wrote the security and usability rules before any code: a separate server, database, login and network path from everything else I run.
  2. Four rounds of independent reviewCodex, an AI reviewer, went through the server patch four times, and a second AI model red-teamed the plan. Each finding was fixed or written down as a known trade-off. The last round's one condition, a test with a real client, was then met.
  3. Kept offline until it passedThe public address stayed switched off until the patched server had passed review.
  4. A real connection across the internetA real RustDesk client reached a test Windows 11 PC through the tunnel and the hardened server, from two different public addresses.
  5. The firewalls, tested twiceA containment test checked that the server can't reach my network, first with its own firewall, then with the router's firewall alone. Both had to pass.
  6. A full dress rehearsalOne continuous run as a brand-new client: setup link, install, code, approve, connect, then unattended access.
  7. Automated testsGo and Rust test suites, plus a real-browser test that walks the whole invite, download, code and approve flow.
